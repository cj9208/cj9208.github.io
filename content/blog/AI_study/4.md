# A First-Principles Architecture for Agent Routing and Safety Harnesses
### Governing Probabilistic Engines with Deterministic Constraints

## 1. Problem Definition and First-Principles Constraints

Deploying Generative AI Agents into production environments—particularly within financial services and highly regulated enterprise systems—presents significant engineering challenges. Traditional end-to-end agent architectures often grant Large Language Models (LLMs) direct execution authority, relying on prompt-level self-assessments to evaluate intent confidence and safety.

This paradigm introduces several fundamental vulnerabilities:

* **Self-Assessment Bias and Hallucination Propagation:** LLMs exhibit "confident hallucinations," where an incorrect intent interpretation is accompanied by a high self-reported confidence score.
* **Correlation Errors and Single Point of Failure (SPOF):** Employing the same model or context window for both intent recognition and self-reflection introduces correlated failures. If the model misinterprets the initial input due to an edge-case prompt or parameter state, the subsequent self-checking step frequently rationalizes the initial error rather than detecting it.
* **Opacity and Auditability Deficits:** Probabilistic scoring mechanisms within a black-box model cannot be unit-tested, reproduced, or mathematically proven to regulatory auditors.
* **Over-Privileged Execution:** Granting an LLM direct API or database execution access creates an unbounded blast radius when non-deterministic outputs occur.

From a first-principles perspective, a production-grade enterprise system must satisfy four non-negotiable constraints:

1. **Classification of LLM Outputs:** An LLM output is fundamentally a probabilistic semantic sample. It must strictly function as an unprivileged **Intent Proposal Generator**, never as an execution authority.
2. **Deterministic Auditability:** Compliance requires verifiable, white-box logic. Every routing decision must be loggable, reproducible, and testable via standard unit testing frameworks.
3. **Risk Asymmetry:** The Cost of a False Positive (FP) varies drastically across business domains. A read-only query carries minimal risk, whereas an unauthorized transactional write carries high financial and regulatory liabilities.
4. **Orthogonal Validation:** Safety mechanisms must operate independently of the primary probabilistic model to eliminate single points of failure and correlation errors.

## 2. Architectural Design: Encapsulating Probabilistic Engines in Deterministic Shells

To address these constraints, the proposed system decouples intent evaluation, validation, and execution. Unpredictability is intercepted at the input layer using deterministic code algorithms, while execution is isolated within a hardcoded runtime harness.

```
                      [ Raw User Input ]
                              │
                              ▼
        [ Router Agent: Pre-processing & Intent Routing ]
          ├── 1. White-Box Deterministic Distance Calculation
          └── 2. Prior Probability Calculation (P_intent)
                              │
         ┌────────────────────┴────────────────────┐
         ▼                                         ▼
   [ High Confidence ]                       [ Low/Medium Confidence ]
         │                                         │
         ▼                                         ▼
[ Evaluate Action Risk Level ]             [ Trigger Dynamic HCI ]
 ├── Low Risk  ──► Autonomous Exec          (Option Chips ≤ 3)
 └── High Risk ──► Mandatory UI Confirm            │
         │                                         │
         └────────────────────┬────────────────────┘
                              │ (User Confirmation / High Confidence)
                              ▼
                [ Model: Output Intent Proposal (JSON) ]
                              │
                              ▼
             [ Independent Context-Isolated Validator ]
                              │
                              ▼
            [ Deterministic Harness Safety Sandbox ]
              (Hardcoded RBAC, Limits, & Parameter Checks)
                              │
                              ▼
                   [ Execution Engine (API/DB) ]

```

### 2.1 Deterministic Distance and Early Interruption

Instead of delegating initial input evaluation to an LLM, the system executes a microsecond-level pre-processing pipeline using white-box algorithms:

* **Algorithm Selection:** Input noise, typos, and semantic offsets are evaluated using algorithmic metrics, including Levenshtein Edit Distance, Jaro-Winkler Distance, Trie-based prefix matching, and topological graph distances across predefined entity schemas.
* **Prior Probability Conversion:** The output metrics are converted into a deterministic prior probability, denoted as $P_{\text{intent}}$.
* **Early Cutoff:** If $P_{\text{intent}}$ fails to meet a minimal threshold, the pipeline immediately interrupts processing before invoking downstream LLM tokens. This evaluation operates in microseconds ($\mu s$), incurs zero token costs, is $100\%$ reproducible, and provides white-box audit logs suitable for unit testing.

### 2.2 Calibrated Abstention and Dynamic HCI

When $P_{\text{intent}}$ falls within an ambiguous confidence interval, the system refrains from guessing intent or invoking high-cost model calls. Instead, it triggers a dynamic Human-Computer Interaction (HCI) step:

* **Option Chips ($\le 3$):** Adhering to Hick's Law, the system generates at most three structured options for the user to confirm.
* **Cognitive Load Reduction:** This mechanism converts probabilistic ambiguity into explicit user authorization with minimal cognitive friction, preventing user fatigue and mis-clicks.

### 2.3 Asymmetric Risk-Based Thresholds

The system enforces non-symmetric confidence thresholds based on the financial and operational risk of the target action:

* **Low-Risk / Read-Only Actions (e.g., Knowledge Base RAG):** Configured with a lower confidence threshold (e.g., $P_{\text{intent}} > 0.65$), prioritizing operational speed and user experience.
* **High-Risk / State-Changing Actions (e.g., Fund Transfers, Account Modifications):** Require a strict confidence threshold (e.g., $P_{\text{intent}} > 0.99$). Even upon passing this threshold, execution requires a mandatory UI-level confirmation with highlighted parameter diffs.

### 2.4 Zero-Trust Execution, Orthogonal Validation, and SPOF Elimination

To eliminate Single Points of Failure and correlated errors:

1. **Orthogonal Redundancy:** The input pre-processing stage relies on symbolic mathematics and deterministic algorithms, which operate independently of the neural network's parameter weights. Even if the LLM encounters a failure mode, the input processing layer remains stable.
2. **Context-Isolated Validator Agent:** If the proposal passes the confidence threshold, it is evaluated by an independent Validator Agent operating in an isolated context window with distinct prompt parameters. This prevents confirmation bias where a single context chain rationalizes its own hallucinations.
3. **Deterministic Harness Sandbox:** The LLM output is strictly formatted as a JSON intent proposal. The proposal is passed to a hardcoded runtime environment (Harness). This Harness independently performs:
   * Role-Based Access Control (RBAC) and authorization checks.
   * Balance and boundary parameter validations.
   * Schema verification.



The LLM is completely stripped of network API credentials and database connection handles.

## 3. Comparison of Architectural Approaches

| Feature / Dimension | Traditional All-LLM Agent | Proposed Deterministic Harness Architecture |
| --- | --- | --- |
| **Routing Mechanism** | LLM Self-Assessment (Black-box, high latency, susceptible to hallucination) | **Deterministic Code Algorithms (Edit/Graph Distance) + $P_{\text{intent}}$** |
| **LLM Privilege Level** | Direct API/Database execution rights | **Unprivileged Intent Proposal Generator** |
| **Validation Layer** | Self-reflection within the same context window (High risk of SPOF) | **Heterogeneous Redundancy: Symbolic Math + Isolated Validator + Hardcoded Sandbox** |
| **Risk Management** | Static, symmetric threshold | **Asymmetric Risk Thresholding (FP-cost dependent)** |
| **Auditability & Unit Testing** | Non-reproducible; cannot write standard unit tests | **$100\%$ white-box logs, reproducible, unit-testable** |
| **Emergency Failover** | Complex conditional prompt branches | **Dynamic threshold adjustment to $100\%$, routing to pre-warmed HITL** |

## 4. System-Level Benefits: Regulatory Alignment and Disaster Recovery

### 4.1 Regulatory Auditability and Compliance

Financial regulators require clear attribution, verifiable logic, and bounded failure states. By migrating routing decisions to white-box algorithms and restricting LLMs to proposal generation, the system produces a complete, deterministic audit trail. Every decision boundary can be verified via automated test suites.

### 4.2 Unified Control Plane and Pre-warmed Failover (HITL)

Emergency fallback mechanisms in software architecture often fail because backup paths remain unexercised until a system outage occurs. This architecture integrates Human-in-the-Loop (HITL) workflows directly into daily operations:

* **Normal Operations:** Marginal-confidence queries routinely pass through the HITL interface, ensuring that human operator queues and routing interfaces remain continuously active and validated.
* **Emergency Fallback:** In the event of a model anomaly or upstream service disruption, system administrators can dynamically adjust the global threshold configuration to $P_{\text{threshold}} \to 1.00$.
* **Zero Blast Radius:** Adjusting the threshold routes all incoming traffic into the active HITL pipeline instantly. The transition utilizes an existing, validated path rather than an unmonitored cold-failover circuit.

```
[ Normal Operation ] ──► Low Confidence Traffic ──► [ Active HITL Pipeline ] (Continuously Exercised)
                                                             ▲
[ Emergency State ]  ──► Threshold Set to 100%   ────────────┘ (Instant Seamless Failover)

```

### 4.3 Graceful Recovery

When normal operations resume, administrators adjust the configuration threshold back to default levels. Traffic redistributes automatically according to risk profiles without requiring service restarts, cache clearing, or state reconciliation.

## 5. Conclusion

Building resilient enterprise AI systems requires accepting the inherent probabilistic nature of Large Language Models. Rather than attempting to eliminate model hallucinations through prompt engineering alone, this architecture uses deterministic engineering controls to enforce safety.

By employing white-box distance algorithms at the input layer, isolating LLMs as unprivileged proposal generators, and enforcing execution within a hardcoded harness sandbox, the system achieves a verifiable, audited, and operationally stable integration of Generative AI within high-stakes enterprise environments.
