## S1 封面

- 主标题：**把判断从生成里拆出来**
- 副标题：DeepEval 的 JEV 与评估的三层演进
- 落款：讲者 / 日期
- 角标（小字）：基于 TypeSafe AI 官方博客《Introducing Jev in DeepEval》《Introducing JevEval》的读后梳理

## S2 开场：先把两个名字分开（30 秒讲清）

标题：**今天有两个主角：JEV 和 JevEval，它们不是一回事**

- **JEV = 一个模型**。TypeSafe 的 "System One"：不生成文本，只对结构化问题返回类型化概率（`P(yes)`、选项分布、量表位置）。
- **JevEval = 一个用法**。基于 JEV 的自定义评估指标：把"评估标准"从一句 prompt 变成一组有类型的问题 + 加权公式。
- 一句话关系：**JevEval 是 JEV 的第三层用法；前两层是把 JEV 塞进 DeepEval 已有指标，第三层才是围绕 JEV 重新定义指标。**
- 讲者备注：用 Kahneman 类比立住直觉——LLM 是 System 2（慢、生成、费力），JEV 是 System 1（快、自动、有界的判断）。观众只要记住"判断模型，不是更小的语言模型"。

## S3 问题：LLM-as-a-judge 用错了工具

标题：**为一个 bit 的结论，付了一整段生成的代价**

- 几乎所有 LLM 评估指标（faithfulness / answer relevancy / safety…）底层都是同一套动作：喂给 LLM → 生成一段话 → parse 出 yes/no 或分数。
- 判断本是**闭式、有界、答案就是一个概率**的任务；生成模型干的是自由文本生成——任务性质和工具错配。
- 三个固有代价：
  - **variance**：同一 case 问两次，措辞不同、结论可能翻转；
  - **cost**：一个 bit 的结论付一整段 token；
  - **latency**：自回归生成，秒级；判断本可以是一次前向。

## S4 JEV 是什么

标题：**语言任务留给 LLM，决策点交给 JEV，公式把决策变成分数**

- JEV：非语言判断模型（non-language decision model），不生成文本，只返回**类型化概率**。
- 三个组件的分工（这页的图）：
  - LLM → 语言密集型抽取（它最擅长的）；
  - JEV → 有界决策（LLM 最不擅长的）；
  - **公式 / 聚合层**（`Σwv/Σw`、权重、阈值）→ 确定性代码，把一堆概率组装成指标分。
- 强调第三个组件：后面会看到，**判断力很大一部分落在公式层**（怎么拆问题、怎么加权），不只在模型。

## S5 JEV 的三个决策原语

标题：**输出是结构化数值，软件用阈值映射结论——不再 parse 文本**

| 原语 | 问的问题 | 返回 | 直觉 |
|---|---|---|---|
| **Noul** | 这个命题成立吗？ | 单个概率 `P(yes)` | →1 强支持，→0 否定，→0.5 模糊 |
| **Choice** | 这组选项里哪个符合？ | 选中项 + 概率分布 + confidence | 不会编造选项、不会格式错乱 |
| **Score** | 在有序量表上落在哪？ | 期望位置，归一化 0–1 | 允许中间值，不硬 snap 到标签 |

- 阈值示例（源文原样）：严格检查 `p >= 0.5`；容忍模糊的检查把 0.35–0.65 全算 undecided。
- 收束句：**判断的"松紧"第一次变成显式的、可版本化的工程参数，而不是藏在 prompt 措辞里的运气。**

## S6 三层阶梯：决策权一步步从 LLM 手里移走

标题：**三层的差别只在一件事：判断由谁、用谁写的问题来做**

- 图（三层并列）：一条 test case →
  1. **hybrid**：LLM 抽 claim，JEV 逐条判（渐进、可回退）；
  2. **system_one**：零 LLM，JEV 答 DeepEval **预设**的整体问题；
  3. **JevEval**：零 LLM，JEV 答**你自己写**的问题。
- 前两层 = 把 JEV 塞进已有指标（safe part）；第三层 = 围绕 JEV 重新定义指标（best part）。
- 讲者备注：点一句"这也是一个渐进替换不可靠组件的通用模板：先在最保险处替换 + 回退兜底 → 撤掉旧组件 → 把设计权交还用户"。

## S7 一条 case 走完 hybrid

标题：**Eiffel case：LLM 只抽取，JEV 判——0.67 不再飘成 1.0**

- case（源文原样）："两条对、一条编"：output 三句话，前两句有 retrieval 支撑，第三句 "designed by Gustave Eiffel" 是真的但**无支撑** → 理想分 2/3 ≈ 0.67。
- 模式 0（纯 LLM judge）当场翻车：模型按"常识"把第三条判成 supported，**0.67 → 1.0**；再跑一次可能又是一个结论。
- hybrid：LLM 只产出 claim 列表；JEV 对每条 claim 测一个 Noul `P(yes)`（示意）：

| claim | P(yes) | 阈值 0.5 |
|---|---|---|
| completed in 1889 | 0.97 | ✅ |
| 330 metres tall | 0.94 | ✅ |
| designed by Gustave Eiffel | **0.08** | ❌ |

- 买到的东西：常识救不回来（问题被界定死）、重跑不飘、三条 batch 一个请求（~100ms、$0.042/M，源文实数）、**每条 claim 的概率可见**（debug 质变）、单条失败退回 LLM（安全网）。

## S8 system_one：抽取被消解，LLM 彻底退出

标题：**不是偷偷抽 claim，而是问题的形状变了**

- 常见疑问：没有 LLM 抽 claim，JEV 判什么？答案：**根本不抽取**——把问题改写成关于整段 output 的、带全称量词的有界问题，一次性问三个预设问题：
  1. 每一条 claim 都被 context 支撑吗？（Noul，示意 ≈0.10）
  2. 有没有任何东西与 context 矛盾？（Noul，示意 ≈0.94——无支撑 ≠ 矛盾）
  3. 整体接地程度多高？（Score，示意 ≈0.55）
- `score = Σwᵢvᵢ/Σwᵢ`；confidence = 最不"决断"的那个答案；reason 由答案**确定性拼出**，不是生成。
- 三个必须说清的边界：
  - **分数不可与 hybrid 直接比**——是另一位裁判的另一个数，切模式要重标阈值和基线（源文专门 callout）；
  - 看不到逐 claim 概率表——细粒度被折叠；
  - 失败模式不同：没有 LLM 可退，case 超出 JEV 上下文直接报错。

## S9 工程账：量级跃迁在 system_one，不在 hybrid

标题：**hybrid 省 1.5x，system_one 省 77x——但便宜是用分辨率换的**

- 单次 faithfulness eval（输入 ~1500 tokens；JEV 侧源文实数，LLM 侧为示意估算）：

| | LLM 调用 | 单次成本 | 单次延迟 |
|---|---|---|---|
| 模式 0 纯 LLM judge | 1（大） | ~$0.0065 | ~2–4s |
| 模式 1 hybrid | 1（只抽取） | ~$0.0043 | ~1–2s |
| 模式 2 system_one | **0** | **~$0.0001** | **~0.1s** |

- 为什么是结构性的：JEV 单次前向、只收 input；LLM judge 延迟 ∝ output token、output 单价 ~5x。
- 三条诚实前提：
  1. judge 换成 mini 档，成本差缩到 ~4x——**但延迟差追不平**；
  2. 规模化才见真章：1 万条门禁 ≈ $65 + 数小时 → ≈ $1 + 数分钟；
  3. **准确率是没被定价的一轴**：官方 benchmark"承诺了、还没给"。

## S10 JevEval：连问题都你自己写

标题：**评估逻辑第一次变成可读、可版本化、可单测的代码，而不是一段 prompt**

- 公式：`JevEval = Σwᵢvᵢ / Σwᵢ`（只对**实际适用**的问题求和）；全程零 LLM，整个指标 = 一次 JEV 请求 + 一点算术。
- 例子 Tool Faithfulness（agent 总结工具返回值，判"有没有编造"）：工具只返回 `temp_c=18, sunny`，output 多说了 breeze 和 humidity——两项是编的。

| 问题 | 原语 | 权重 | 映射值（示意） |
|---|---|---|---|
| 每个事实都出现在工具输出里？ | Noul | 2 | 0.05 |
| 工具返回的值都报准了？ | Noul | 1 | 0.95 |
| 整体接地程度？ | Score | 1 | 0.33 |
| 对工具没返回的信息怎么处理的？ | Choice（`stated_it_as_fact`=0，`nothing_missing`=None→剔除） | 1 | 0.0 |

- score ≈ 1.38/5 ≈ **0.28**。
- 三个设计点：两个 Noul 各判一件事（拆开才看得清"报得准但多编"）；weight 是你的价值判断；Choice 的 `None` 实现"本题不适用"。

## S11 最容易问的问题：这和"LLM + Pydantic 结构化输出"差在哪？

标题：**type-safe ≠ decision-safe：schema 校验的是类型，JEV 换掉的是计算**

- 像：都递给你一个结构化数字。不同：**数字的来源**——Pydantic 里的 `confidence=0.8` 仍是自回归**生成**的 token（"看起来很合理"）；JEV 的 `P(yes)` 从真实决策分布**测出**（经过校准）。
- 三个后果（都是结构化输出碰都没碰的）：
  - **阈值只对校准概率有意义**——LLM 的 confidence 跨调用不可比、众所周知过度自信，threshold 它等于 threshold 噪声；
  - **variance 一点没减**——schema 保证形状不保证稳定；
  - **cost/latency 反而可能更高**——完整生成照付，还多付 JSON 外壳。
- 类比：给不可靠的服务定了规范的响应格式——修的是接口契约，不是底层计算。
- 公平话：Choice"不编造选项"这点 enum 也能做；但 LLM 给的选项概率分布仍是生成的、未校准的。

## S12 取舍与存疑（我的判断）

标题：**三层的取舍不在自动化程度，在"粗 vs 精"和"问题谁写"**

- system_one 是**省事的粗判**：全称合取"每条 claim 都被支撑吗"→ claim 越多 P(yes) 天然越低，**分数混进了 output 长度**（20 句编 1 句比 3 句编 1 句分更低，忠实率其实一样）；hybrid 的 supported/total 天然对长度归一。
- 澄清一个易错点：system_one 不是"更不稳"，是"分辨率更低"——variance 反而更小；**真正会飘的是 hybrid 那步 LLM 抽取**（这次拆 1 条 claim、下次拆 2 条，分母就变了）。
- JevEval 是**费心的精判**：分解和标定全归你，且 `Σwv/Σw` 是钝聚合器——**表达不了一票否决**（真实判断很多是 min/veto 结构；例子里压到 0.28 是 weight=2 + Choice 恰好给 0 手工凑的）。
- JEV 自己也会幻觉，但它把"不可测的错"变成"**可测的错**"：能画可靠性曲线、能事后重标定、能说出"阈值 0.65 误放率 3%"——LLM 生成的 confidence 这句话永远说不出来。校准是总体性质、不是单例保证；红利只在"可聚合、可标定、要设门禁"的场景兑现。
- 存疑：accuracy / calibration 目前是**主张而非实测**——官方 benchmark 承诺未兑现，校准曲线缺席。

## S13 收束：怎么落地

标题：**别把"更快更省"直接当成"更好"——按场景选层，自己回归一遍**

- 一句话主线回收：**把判断当成有类型、可校准、可设阈值的一等公民输出**——variance 从 prompt 玄学变成 confidence + threshold 的工程参数，这对 CI/CD eval 门禁是质变。
- 行动建议：
  - 想试水 / 要逐条 debug → **hybrid**（可回退，安全）；
  - 高量级门禁、成本延迟敏感 → **system_one**（但先重标阈值和基线，别拿分数跨模式比）；
  - 有自定义判断逻辑、想版本化 → **JevEval**（接受分解与标定成本）；
  - 切换前：拿自己的标注集回归一遍，重点盯抽取复杂、跨句推理、output 偏长的 case。
- 接入两行命令（源文原样）：`deepeval set-eval-mode hybrid | system_one`；`pip install typesafe-sdk`。
