# 在梦里改策略：Dream-RSI 把发现历史变成回放模拟器，与"可复制的是编排层、不可复制的是被冻结的执行现场"

> 这是一篇读后梳理，不是翻译。主线一句话：**RSI 的瓶颈已经从"生成更好的解"上移到"改进那个决定去哪里生成解的策略"，而这个 meta 层的反馈既延迟又昂贵；Dream-RSI 的解法是把已经付过钱的在线探索结果冻结成一台离线评估机，于是策略改进从 online trial-and-error 变成 offline replay——代价是这台机器的支持域永远等于过去实际走过的那条路。**

## 一、一句话主线

论文表面在做"自动科学发现"，实际动的是它上面那一层。AlphaEvolve、SimpleTES、EvoX 这一批系统已经把"生成候选 → 评估 → 精化"这个对象层循环卷得很密，但决定**往哪个方向生成、开几条分支、并行多少、什么时候停**的那一层，长期是一段人手工写死、跑完就丢的循环。Dream-RSI 的主张是：这一层也该被优化，而且优化它的监督信号已经存在——就在上一次探索留下的执行记录里。

核心概念要先钉精确：**已完成的发现历史不是一个 context，是一个 replay simulator**（源文用 "replay simulator" 和 "worlds" 互指）。一次跑完的 discovery 过程天然记录了"过去的探索决策 + 它们的真实代码执行结果"，组织成 discovery tree 之后，一个替代策略可以在这棵预录树上走不同的分支子集、不同的顺序、不同的并行分组、不同的停止点——**所有执行结果都已存好，评估新策略只需读记录，不必重跑 discovery agent 或 evaluator**。源文给的类比是 model-based RL 与 World Models / Dreamer 家族：agent 从经验里学一个动力学模型，然后在模型内想象轨迹来改进策略。

这个类比在一个关键点上很松，也是本篇 §七 的起点：**Dreamer 的 world 是学出来的、能想象没走过的轨迹；Dream-RSI 的 world 是录下来的、生成能力为零。**它更接近一张带结构的 memoization 表，而不是一个 world model（这条判断是我的分析，源文只做了类比、没讨论差别）。

## 二、域背景：为什么 meta 层的探索优化这么难（我的分析，非源文）

源文给了两个瓶颈的陈述，但没展开这两个瓶颈为什么在物理上这么硬。这一节是我的领域推理，用来交代后面困难集从哪来。

**meta 层的反馈单位和对象层差了一个量级。** 评估一个候选解，跑一次 evaluator 就有结果。评估一个探索策略，必须让它跑完整整一轮 discovery——源文的预算是一轮 110 次 agent 调用（Gemini-3.1-Pro：10 条并行分支 × 最多 11 次 refine）——再看这一轮的总产出。而且这一轮里每一步都是随机的：源文明确写"这个 transition 是随机的，因为 discovery agent 从同一个起始工作区可能生成不同结果"。所以你还得多跑几次才能分清"策略差"和"这次运气差"。样本效率被压到极低，这才是"延迟且昂贵"的真正含义。

**它落在 test-time compute 的账本上。** 探索策略本质上就是"怎么花推理预算"的策略。预算花错方向不是浪费一点钱，是整轮 discovery 白跑，而下一轮的模拟器池也就少了那一部分记录。

**为什么固定策略在长程下必然失效：搜索空间的形状在过程中是变的。** 开局到处是低垂果实，任何方向的 refine 都涨；中局好方向被挖穿、收益递减，此时正确动作是换方向而不是继续深挖；末局只剩硬骨头，需要的是耐心和资源集中。一个写死的策略只能在一种地形下最优。源文 §5.2 那条"性能上升时省算力、停滞时把算力加回来"的曲线，本质就是策略在追踪地形变化——这是我在那组数字里读到的东西，源文只描述了现象。

**为什么"把历史写成建议塞进 prompt"这条最自然的路走不通。** 这是源文 §5.1 的实验结论，我把它放在域背景里，因为它解释了整个设计的形状：既然蒸馏成语义指导有害（详见 §六），那历史就必须以**可执行的结构**而非**可读的建议**的形式被消费。整篇论文的机制都是从这个约束倒推出来的。

## 三、discovery tree 与 replay 到底是什么（worked case）

这一节用一个 3 分支的小网格把机制走完。**格子里的分数是我编的示意值，非源文数字**；树的规则、API、打分公式、终止条件都是源文原样。

### 3.1 树在物理上就是磁盘上的一棵目录树

不是抽象数据结构。源文 Appendix B 的在线探索 prompt 写得很实在：每个节点是一个 `attempt_*/` 目录，里面有 `proposal.md`（这次的机制是什么、从历史里找到什么证据、为什么不是重复）和实际实现代码，旁边配 `eval/score.json` 和失败时的 `error.txt`。节点还保存 filesystem snapshot、生成的 artifact、评估诊断和分数 `s_v`，分数遵循固定的 task-scoring 协议，越大越好。

树的硬约束只有一条：**每个非根节点恰好有一个 primary parent**，即"这次尝试从哪个工作区接着跑"。根 `r` 是初始工作区。所以一条从根往下的链 = 一个方向被反复 refine；根的不同子节点 = 语义上不同的方向。

### 3.2 探索策略是一段只做"分配"的代码，它自己不解题

策略不是 prompt，是一个 Python 类：`OptimalPolicy.solve(self, question, budget=None)`。源文 prompt 第二段就写着 **"Do not solve the scientific task and do not edit any other program."** 它能看到的只有一个很小的类型化 API：

| 调用 | 返回 |
| --- | --- |
| `question.observed()` | 已揭示的前缀 → `Observation(branch, attempt, score, evaluated, valid, fail_class, error, delta_vs_baseline, delta_vs_parent, n_valid, n_total)` |
| `question.legal_actions()` | 当前合法动作 = 未开的根 + 已开分支的前沿 |
| `question.legal_roots()` / `opened_branches()` | 只列未开的根 / 已开的分支号 |
| `question.meta(cell_id)` | `.branch .attempt .parent_id .seq .tags` |
| `question.probe_batch(cells, on_reveal=...)` | 提交一批格子去执行 |
| `question.max_parallelism` | W，并行 worker 数 |

每轮它只做一个决定：**这一批发哪几个格子**（批大小 ≤ W）。发一个未开的根 = 开新方向；发某条分支的前沿 = 在这个方向上再 refine 一次；发空批 = 停。写代码、跑评估的是底下那个**全程不变的 coding agent 和 evaluator**。源文原话：只有 exploration-policy 代码在变，底层模型、evaluator、执行接口全部固定。

这就是"轻量编排层让探索变得显式、可编程"的字面含义——meta 层优化第一次有了一个明确的作用对象：一段可编辑的代码。

### 3.3 replay = 同一份策略代码，换一个 transition

在线与离线**共用同一个 decision interface**（同一套可行批集 `A(T;W) = {C ⊆ A(T) : |C| ≤ W}`、同一个批次概念、同一个轮次计数），唯一差别是选中一个节点之后发生什么：

- **在线**：调用 discovery agent，它从父节点保存的工作区继续、拿累积观测当 context，生成新候选，evaluator 真跑一遍 → 产生一个新子节点。**随机**，而且**贵**。最多 `K1` 轮。
- **离线回放**：不调用任何 agent 或 evaluator。直接返回该节点**已录下来的子节点**，把分数、`fail_class`、诊断一起揭示给策略。**确定**，成本**零**（只读记录）。最多 `K2` 轮。

`Child(v; T_i, T^{m,k}_i)` 的规则：对 `v ≠ r`，返回它在记录里那个唯一的、尚未被揭示的子节点；对 `v = r`，返回"记录里最早创建、且还在已观测子树之外"的那个子节点，即开一条此前没揭示过的分支。没有记录可返回时 `Child = ∅`。回放终止于三种情况之一：策略选了空批、轮数达到 `K2`、或 `T^{m,k}_i = T_i`（整棵树都已揭示）。

于是同一份 `solve()` 扔进回放器就能立刻跑完，而且因为树有限、结果全存着，一定终止。**一次昂贵的在线跑，换来成千次零执行成本的 off-policy 评估**——这就是 "dreaming" 的字面含义。

### 3.4 为什么这样就能判断策略好坏：给轨迹打分

策略在回放里走出一条轨迹 = 一个**子集**（翻了哪些格子）+ 一个**顺序** + 一种**分批方式** + 一个**停止点**。源文 Eq(1) 给这四件事一起打分：

```
V_i^m = max_{v ∈ T_i^{m,k*}} s_v  −  β₁·N_i^m  +  β₂·N_i^m / max{1, k_i^{m,★}}
              发现质量                执行成本            并行度奖励
```

`N_i^m = |T_i^{m,k*}| − 1` 是揭示的非根节点数（即这条轨迹代表了多少次真实的 generation–evaluation 请求），`k` 是完成的决策轮数。第三项是"平均每轮跑了几次尝试"，专门奖励把独立的有希望探针打成批、而不是串行发。策略总分是它在固定历史上所有树的平均：`V^m = (1/t) Σ_{i=1..t} V_i^m`。

实现里更细：evaluator 扫策略内部那个 `beta` 旋钮，按 `pareto.reward = pareto.auc − lambda * parallel_penalty` 排序，其中 `parallel_penalty` 是 `effective_sequential_rounds / total_probes` 在 sweep 上的均值；一个大小为 `k` 的批次在 `W` 个 worker 下花掉 1 个决策轮和 `ceil(k/W)` 个有效串行轮，所以纯串行策略 penalty ≈ 1，有用的满批接近 `1/W`。

### 3.5 三个策略在同一份冻结历史上回放（示意分数）

设 W=3，一次在线探索冻结出这张网格：分支 A 四层记到 0.42 / 0.55 / 0.61 / 0.63；分支 B 四层记到 0.40 / **FAIL（`fail_class = compile_other`）** / 0.78 / 0.81；分支 C 只有两层 0.41 / 0.44（这条分支在线就没跑下去）；分支 D 从未被开出。取 β₁=0.02、β₂=0.05：

| 策略 | 走法 | N | k | 最好分 | N/k | penalty | V |
| --- | --- | --- | --- | --- | --- | --- | --- |
| P1 串行深挖 | 每轮只发一格，A 挖到底再挖 B 再挖 C | 10 | 10 | 0.81 | 1.00 | 1.00 | 0.660 |
| P2 批量 + 失败分类 | 先开三条分支，B 撞编译错误判为可修复、继续挖 | 8 | 4 | 0.81 | 2.00 | 0.50 | **0.750** |
| P3 见错就关分支 | 同样会打批，但把 `compile_other` 当算法失败、永久关闭 B | 8 | 4 | 0.63 | 2.00 | 0.50 | 0.570 |

P3 与 P2 的对比最能说明这套机制在优化什么：**成本、轮数、并行度完全一样，唯一差别是怎么解释一次可修复的失败**，于是最好分数从 0.81 掉到 0.63。它优化的不是解，是"怎么分配搜索、怎么解释证据"。

选择规则（源文）：候选集**包含当前正在用的策略** `π_t^0 = π_t`，取 `π_{t+1} = π_t^{m★}`，`m★ ∈ argmax V^m`，因此 `V^{m★} ≥ V^0`——选出来的策略在固定历史 `H_t` 的平均回放分上不劣于当前策略。

### 3.6 支持域边界：`Child(D1) = ∅`

分支 D 在这次在线探索里从没被开出过，冻结的树里没有它的任何记录。回放器不能生成新结果，它只能揭示真实发生过的事。所以：**回放模拟器的支持域，恰好等于过去那些策略实际走过的那条路。** dreaming 能回答"在这批已知结果里怎么分配探针更划算"，不能回答"某个从没试过的方向本来会很好"。

源文自己把这条边界写进了 prompt：`GridPlan(branch_count=W, refine_count=R)` 在回放中若请求超过冻结 trace 的 `context.trace_branch_count` / `context.trace_refine_count`，就是 out of support、**cannot earn replay reward**。§七 会把这条边界的后果推到底。

## 四、困难 ↔ 方案 咬合（核心，按四层）

### 编排层：解决"策略隐含在 agent 里，无法被单独优化"

| 困难 | 方案 | 为什么这么解 |
| --- | --- | --- |
| 探索策略藏在 coding agent 的 prompt 与循环里，没有可编辑的实体，meta 层优化找不到作用对象 | 轻量编排层接管 branching / 并行 / 停止，底层 coding agent 完全不动；策略落成一段代码 `OptimalPolicy.solve`，prompt 明写"Do not solve the scientific task" | 只有把策略变成可读、可版本化、可 diff 的代码，LLM 才能改它、回放器才能跑它；不动 agent 则保证对照实验的差异只能归因于策略 |
| 在线与离线两套语义容易漂移，改好的策略上线可能不是同一件事 | 两阶段共用同一个 decision interface（`A(T;W)`、批 `C`、决策轮计数），只在 transition 上分叉：在线生成新子节点（随机），离线返回已记录子节点（确定） | 同一份策略代码在两边跑出同构的轨迹，回放里的改进才能直接迁移到线上 |
| 一次尝试到底算"新方向"还是"深挖"，需要一个统一的动作语义 | 动作 = 选一个节点批。选根 `r` = 开新分支，选叶子 = 在该分支上 refine，选空批 = 停 | 把"宽度 vs 深度"从两种不同的操作折叠成同一种操作的两个取值，策略代码因此可以很短 |

**这一层的原则**：先让决策变成数据，再谈优化决策。

### 历史层：解决"meta 反馈延迟且昂贵 + meta 策略空间巨大"

| 困难 | 方案 | 为什么这么解 |
| --- | --- | --- |
| 评估一个策略要观察它如何塑造后续许多 proposal–evaluation 周期，反馈单位是"一整轮"而不是"一次调用" | 已完成的 discovery history 直接当 replay simulator：所有执行结果已存在树里，评估新策略只需读记录 | 把 meta 层一次评估的成本从"一次长在线 rollout"降到"一次树遍历"，源文称一次昂贵在线跑可支撑成千次零执行成本的 off-policy 评估 |
| 新提出的策略可能很差，需要试很多替代方案 | 每个离线周期构造并评估 `M ≥ 1` 个策略版本，每个版本在历史里**每一棵**树上都单独回放，回放反馈在版本之间回传给 policy-development agent | 多棵树取平均是唯一的泛化压力：策略必须在多份历史上都不差，才不会被单棵树的偶然形状带走 |
| 冻结网格是有限的，策略只要背下"哪个 cell 会赢"就能把回放分刷满 | **prefix-only 硬约束**：决策只能用已揭示的观测、`baseline_score`、合法动作集、结构化 `meta` 和 helper 信号；明令禁止未揭示分数、真实最优值、硬编码 winning cell id、绝对分数阈值；`policy_execution_traces.jsonl` 只许轮间使用，**绝不允许在 `solve()` 里读**，也不许把 trace 特定的分支号/cell id/分数/目标抄进策略逻辑 | 这是 meta 层的 anti-reward-hacking 护栏。注意它的形态是**限制策略能看到什么**，而不是加固评分函数——§七 会回到这一点 |
| 回放里一次可修复的失败会永久饿死一条其实有希望的分支 | 失败四分类：hard-unrecoverable / repairable implementation failure / weak-but-underexplored / repeatedly unpromising after sufficient valid evidence；成功语义钉死为 `error is None && fail_class == "ok"` 即成功评估，**哪怕 `valid == False`**；"后来的一次成功会重开分支，并取消仅基于早期失败的关闭"；`compile_other` 单独点名"不构成永久性 hard" | 输出/正确性不匹配、共享内存与资源上限、变量/代码/mask/layout/shape 错误通常可修复。把这类错误当算法失败，等于用一次编译器抖动误杀整个搜索方向——§3.5 的 P3 就是这个错误的代价 |
| 只看最新观测或最高分会丢掉分支的形状 | 要求为每条已开分支重建**有序前缀轨迹**：成功锚点、分数趋势、回退、失败/修复序列、已探与剩余深度；排名只能用前缀导出的信号（父→子增益、完整轨迹、真实成功 vs 失败证据、失败可修复性、既往修复结果、剩余深度、跨分支比较） | 一个浅层弱分不足以丢弃分支，更深的尝试可能翻盘；这是把"探索耐心"编码成可读的证据规则，而不是一个温度参数 |

**这一层的原则**：历史要以可执行的结构被消费，不能以建议的形式被消费。

### 目标层：解决"质量、成本、并行三者的取舍"

| 困难 | 方案 | 为什么这么解 |
| --- | --- | --- |
| 只奖质量会让策略狂刷探针，只罚成本会让它早停 | `V = max s_v − β₁N + β₂·N/max{1,k}` | 三项分别对应发现质量、执行成本、并行度；第三项奖励"每轮平均跑几次尝试"，逼策略把独立的有希望探针打成批 |
| "会不会打批"这件事在单项分数里看不出来 | `pareto.reward = pareto.auc − lambda·parallel_penalty`，`parallel_penalty = mean(effective_sequential_rounds / total_probes)`，串行 ≈ 1、满批 ≈ `1/W`；evaluator 扫一个固定的 beta 网格 | 把批量能力变成一个可直接排序的量；扫网格同时检验"这个策略是否真的暴露出 attainment/work/parallelism 的权衡"——源文说 beta sweep 非退化的前提是 beta 真的改变了这个权衡 |
| 策略改坏了无法回退 | 候选集包含当前策略，取 argmax ⇒ `V^{m★} ≥ V^0` | 单调不退化——但注意这个保证的作用域是**固定历史上的平均回放分**，不是在线表现（§七） |
| 宽度 vs 深度该给多少，不能靠 runner 的 fallback 默认值 | 每个策略**必须**实现确定性的 `plan_grid(context) -> GridPlan`，在新 live grid 创建**之前**运行，**禁止查看当前 episode 的任何结果**，且必须总返回非 `None` 的 plan；按证据规则调 `branch_count` / `refine_count`：多种语义不同的根早期就涨而深化停滞 → 加宽减深；高收益来得晚且集中在少数可重复方向 → 减宽加深；所有已探方向到足够深度后停滞但仍有方向类未覆盖 → 加宽；反复不可恢复失败或方向高度冗余 → 保守收窄；历史不足或证据冲突 → 显式返回保守 bootstrap plan 并说明证据不足 | 把"给多大搜索空间"也变成有证据、可解释、可复现的代码路径。每个 plan 必须带一句事实性的 `reason`。运行时 grid 是硬上界：控制器阈值可以少用，但永远不能创造出超出 plan 的分支或尝试 |
| `beta` 一个旋钮承担多重含义，策略容易在 episode 内乱改 | 明确拆成三种角色，prompt 里写"Do not conflate them"：① 一次 replay 或 live episode 内 beta 固定，所有行为阈值走同一个 `_schedule(beta) -> dict`，禁止在 `solve()` 里根据观测改 beta；② 离线评估扫固定 beta 网格，这**不是**在线 beta 自适应；③ 提下一版策略时用**此前 live 周期**的证据一次性选定 baked-in 默认值——live best 仍在涨就保持原值除非 sweep 明显指出附近有更优；已停滞且更高 beta 在合理 work/parallelism 代价下能拿到更高 attainment 就上调约 0.1–0.2（clamp 到 [0,1]）；高 beta 已试过一整段停滞且 sweep 显示只增工作量不增 attainment 就下调；历史不足或证据冲突则取中等探索的默认值约 0.6 | 防止把"离线扫参"误当成"在线自适应"，也防止不可复现。源文还特别警告：不要简单地把默认 beta 选成"能摸到冻结 trace 已知上限的最小 beta"——那是在拟合回放天花板，而不是在选一个能上线的停止信号 |

**这一层的原则**：每一个自由旋钮都要写清它有几种角色、分别在什么时刻被谁读取。

### 对象层：解决"discovery agent 自己会重复、会自我吹嘘、会跑偏"

这一层不变（agent 全程固定），但源文把它的 prompt 也公开了，几条约束值得记：提新方案前**必须读完每一个** sibling `attempt_*/` 下的 `proposal.md`、`$history_dir`、`$baseline_dir`（不是抽样、不是只看最近几轮或当前分支），并读对应的 `eval/score.json` 与 `error.txt`，**信实测结果而不是 proposal 对自己的宣称**；对每次失败要分清"核心想法就错"还是"好想法被 bug / 坏参数 / 实现疏漏拖累"——前者不要重复，后者值得重试，但**只有在真的定位到代码里的 bug（不是从 proposal 猜）且手里有具体修法时**；若已试过的东西大多聚集在同一个机制的小变体上且收益变平，那就是局部最优，**要刻意选一个结构上不同的机制或没试过的组合，而不是更安全的边际微调**；只许写 `$node_dir/proposal.md` 和 `$node_dir/$eval_program`，其余全只读；"在被真正评估之前，不要声称它能编译、是正确的、或超过了 SOTA"；绝不执行 `pkill` / `kill` / `killall`。

### 还没解掉的瓶颈

源文没有单独的 limitations 章节。以下是我从正文与 prompt 里读出来的、它自己承认或明显留白的部分：回放请求超出冻结 trace 的规模即 out of support、拿不到奖励（源文明写）；beta sweep 只有非退化时才有意义，即它可能退化（源文明写）；`plan_grid` 在历史不足时只能返回保守 bootstrap plan（源文明写）；离线回放分与在线表现之间的一致性没有单独验证（源文未报告，我的观察）。

## 五、标杆案例：ConvDiv 上 E0–E8 的策略演化（源文数字）

源文 §5.2 给的是 ConvDiv 这一个任务上九轮递归的完整轨迹，这是全文唯一能看到"策略本身怎么变"的数据。

| 轮次 | E0 | E1 | E2 | E3 | E4 | E5 | E6 | E7 | E8 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| round-best performance（1/ms） | 0.427 | 0.625 | 0.855 | 1.403 | 1.488 | 1.499 | 1.770 | 1.880 | 1.898 |
| 本轮 evaluated attempts | 110 | 110 | 87 | 80 | 50 | 92 | 80 | 91 | 86 |

源文的解读：策略表现出清晰的自适应模式——性能上升期它主动节省 discovery 算力（attempts 从 110 降到 50），随后进展停滞时又把探索强度加回去，且这与 further performance gains 同时发生。

把每一段变化对应回具体能力（对应关系是我的分析，数字是源文的）：

- **E0 → E1（0.427 → 0.625，attempts 不变）**：这一跳只能来自编排层与共享 decision interface——预算没变、agent 没变，变的只有那段策略代码。
- **E1 → E4（0.625 → 1.488，attempts 110 → 50）**：省下的算力来自 Eq(1) 的成本项 `−β₁N` 与 `parallel_penalty`。回放器会直接惩罚"翻了 110 格才拿到某个分数"的轨迹，于是策略学会更早剪枝、更满地打批。
- **E4 → E5（1.488 → 1.499，attempts 50 → 92）**：停滞触发了 `plan_grid` 的加宽规则和 beta 跨周期默认值规则——"live best 已停滞且更高 beta 在合理代价下能拿到更高 attainment → 上调默认值约 0.1–0.2"。这是全套 prompt 条款里最直接对应到这段曲线的一条。
- **E5 → E8（1.499 → 1.898，attempts 92 → 86）**：加宽之后的收益兑现，同时成本重新收敛。

对照组同样重要：源文 §5.1 做了一个 `+Guidance` 变体，把历史抽象成高层方向性洞见直接注入 prompt 作为语义引导，结果**在 Dream-RSI 和 Recursive Fixed Exploration 两边都稳定差于不加引导的版本**（Figure 5，ConvDiv）。源文的解释是：长程发现里同时部署多条并行探索线程时，对后续搜索方向施加强语义归纳偏置会过度约束搜索空间、阻碍多样探索。这条负结果与 ReasoningBank / SkillOS / ACE 那条"把经验蒸馏成记忆与技能"的路线正面冲突，是全文我认为最有迁移价值的部分。

## 七、批判：这是一个局部优化器，而致命的那层局部不在优化器里（我的分析，非源文）

### 7.1 "局部"有三个不同的意思，得分开说

**优化器的搜索形态是局部的。** `M` 次修订从 `π_t` 出发、argmax 的候选集包含 `π_t`、单调不退化、没有种群、没有重启、没有多样性压力——这就是一个带 LLM 变异算子的贪心爬山。`V^{m★} ≥ V^0` 这个被当作保证来陈述的性质，恰恰是爬山法的签名，不是全局优化的签名。

**目标函数的视野是局部的。** `V` 是单集内的标量，在旧策略生成的冻结历史上取 in-sample 平均；真正想要的是下一轮的在线表现，而这两者之间论文没有做任何相关性验证。

**可达空间是局部的。** 支持域等于已经走过的那条路（§3.6）。

但"局部优化"这个标签在一个地方会误导：**被优化的对象不是解，是一段作用域全局的规则。** 改一次 `solve()`，所有分支、所有轮次、下一轮在线探索的访问方式全跟着变。准确的说法是"在策略代码空间里做局部搜索，但每一步移动的作用域是全局的"——这与通常贬义的"在当前解附近小步微调"不是一回事。

### 7.2 采样分布被优化器自己锁死

闭环是这样耦合的：`π_t` 决定在线往哪里采样 → 采样结果决定 `H_t` 里有什么 → `H_t` 决定回放能评估什么 → 回放评估决定 `π_{t+1}` 往哪改。没有任何外力打破它。如果 `π_t` 系统性地不开某一类分支，那类分支永远不会进池子，回放器就永远无法证明"开那类分支是好的"——**不是因为证据不足，是因为这份证据在物理上不可能被生成出来**。

这比"优化器是爬山"严重得多：爬山至少能沿着已有维度走到底，而这里是**维度本身被上一轮的策略裁剪掉了**。这是 offline RL 里数据收集策略与目标策略耦合的老问题，只是这里连"用重要性加权修正"的余地都没有——回放是确定性的查表，不是对随机环境的重加权估计。

### 7.3 唯一负责扩张支持域的部件，恰好是奖励无法评分的那个部件

`plan_grid` 的规则明写着"所有已探方向在足够深度后都停滞、但仍有有意义的方向类没覆盖 → 加宽"。可同一段 prompt 又说：请求超出冻结 trace 的 `trace_branch_count` / `trace_refine_count` 就是 out of support、拿不到回放奖励；而且 `plan_grid` 禁止查看当前 episode 的结果。于是"加宽到没覆盖的方向类"这个决定**在回放里得零分**。它只能靠 LLM 读散文规则的先验去执行，闭环既无法验证它对不对，也无法通过 argmax 把它选出来。

再往下一层：回放目标里没有任何信息增益项。`max s_v` 让覆盖变成工具性的（要拿到最深那格就得开那条分支），不是终值性的；`β₁` 罚探针数；`β₂` 奖的是吞吐而非覆盖。所以在回放里，"探索"被彻底化约成"用最少的探针走到已知最好的那格"——**纯粹的地图阅读，不是地图绘制**。而在线阶段开一条新分支的真正价值是它给下一轮的池子添了新格子，这个价值回放器表达不出来。

把 7.2 与 7.3 合起来就是一句可以带走的话：**在这个系统里，奖励密度和任务重要性成反比。**"利用已知地图"有稠密、可排序、单调的信号；"画新地图"只有散文规则、没有信号。

### 7.4 公道话：局部在这里可能是成本上正确的

meta 层反馈昂贵本来就是这篇的出发点，贪心爬山 + 单调性 + 零执行成本评估是划算的组合；换成种群或全局搜索，刚省下来的预算又花回去了。

而且系统确实有一个逃离局部的机制，只是它不在优化器里，在**数据累积**里：`H_t = H_{t-1} ∪ {T_t}`，池子每轮变大，下一轮的爬山是在更大的地图上做的；再加上 `V^m` 要在 `t` 棵树上取平均，逼策略在多份历史上都不差，这是一种弱泛化压力。所以更准确的描述是"**局部优化器 + 不断扩张的支持域**"——把全局化外包给了数据，而不是算法。问题只在于：扩张的方向由优化器自己决定（见 7.2）。

### 7.5 两个便宜的证伪探针

1. **加一个覆盖项**：给回放目标加一个显式的 coverage / novelty 项（奖励翻开此前未被任何历史策略触达过的分支，或让超支持域的 `plan_grid` 请求拿到一点小额外回报），看在线表现是否改善。变好 → 原目标确实缺这一项；变差 → §5.1 那条"强语义归纳偏置会过度约束搜索"在 meta 层同样成立，那他们的设计反而是自洽的。这是个便宜的 ablation，论文没做。
2. **纯诊断，不改系统**：把 `t` 棵历史树的并集画成 branch × depth 覆盖热图，看第 5、第 10 轮时还有多少格子是第 1 轮就没被任何策略碰过的。覆盖率随轮次饱和 = 锁死的直接证据；持续有新格子被开出来 = 7.2 这条批评不成立。

### 7.6 另外三条独立的存疑点（我的分析）

**换序回放的反事实偏差。** 在线探索 prompt 的第一条硬要求就是"读完每一个历史 proposal 再提新方案"，即节点的产出依赖当时的全局历史。但回放把分数当作节点的固有属性、与访问顺序和访问子集无关。策略 P2 在第 3 轮才翻开 B3，而线上 B3 是在"B1、B2 已失败过、A1–A3 也已存在"的上下文里生成的——回放揭示的那个 0.78，严格说不是 P2 在那一步会得到的东西。源文的形式化用"每个非根节点恰好一个 primary parent、结果挂在节点上"绕过了这个问题，没有讨论。

**成本口径只计 discovery-agent calls。** 回放确实零执行成本，但"做梦"不是免费的：policy-development agent 每个离线周期要读轨迹、改 `M` 版策略代码，每版还要在 `t` 棵树上按 beta 网格跑完回放。这部分 LLM 开销在报告的 compute 里看不到。所以"162×""1.7×"是**发现调用**的节省，不是总 LLM 支出的节省——这两个数在 meta 层很重的系统里可能差得不小。

**`+Guidance` 那条负结果的解释可能过头了。** 源文把"语义引导有害"归因于强归纳偏置过度约束搜索空间。但另一种同样自洽的解释是：他们的 guidance 是从历史里抽象出来的**方向性结论**，而历史里的高分方向恰恰已经被挖过——注入它等于让 agent 重复已饱和的方向，这与在线 prompt 第 3 条"不要收敛进局部最优"直接打架。若是这个原因，那结论应该是"不要注入关于**已探方向**的评价"，而不是"不要注入语义指导"。源文没有做区分这两者的消融（例如只注入"哪些方向已饱和、请避开"这类**否定性**指导）。

### 7.7 与站内《The Search Pathology》的正面分歧

那篇的主张是：搜索在不完美代理（单测套件、PRM）上放大会触发 Goodhart 与 reward hacking，解法是把力气**从约束搜索算法转向加固评估地形**（多维代理集成、对抗式 PRM 训练、动态执行追踪、property-based 测试生成）。Dream-RSI 恰好反过来——evaluator 全程固定，所有力气花在优化搜索的分配策略上。

但它并非没意识到 Goodhart：prefix-only 硬约束、禁止把 trace 特定的 cell id / 分数 / 目标值抄进策略逻辑、`policy_execution_traces.jsonl` 只许轮间使用，这三条就是 meta 层的防作弊护栏。分歧点因此很清楚——**它的护栏是限制策略能看到什么，而不是加固评分函数**。而 `V^{m★} ≥ V^0` 是在代理指标上的单调性，所以 Goodhart 在 meta 层照样适用：一个策略完全可以在回放分上稳步上升、在线表现原地踏步，而这套机制内部没有任何东西能察觉。

## 八、收束：可复制的是编排层与那两段 prompt，不可复制的是被完整冻结的执行现场

**可复制的通用件**——已经被论文正文、Appendix A/B/C 和开源代码彻底商品化：

1. 三阶段闭环（在线探索 → 构造回放模拟器 → dreaming 改策略 → 重新部署）。
2. discovery tree 的数据模型（单一 primary parent、节点携带 snapshot / artifact / diagnostics / score）与在线离线共用的 decision interface。
3. Eq(1) 的三项回放目标，以及 `pareto.auc − lambda·parallel_penalty` 的实现形态。
4. prefix-only 约束与"trace 特定信息只许轮间使用"这条纪律。
5. `beta` 的三种角色拆分与跨周期默认值规则（含 0.1–0.2 步长、约 0.6 的保守默认）。
6. `plan_grid` 的宽深证据规则与"必须总返回非 None plan、必须带事实性 reason"。
7. 失败四分类与成功语义（`error is None && fail_class == "ok"`，哪怕 `valid == False`）。
8. **两段完整 prompt 全文**（在线探索 + 回放式策略改进）与发现的 Lasso solver 完整 C++ 实现。
9. §5.1 那条负结果：不要把历史蒸馏成 prompt 里的方向性建议。

**不可复制的壁垒**——收在这里：

- **一份把每个节点的执行现场都完整冻结下来的历史。** filesystem snapshot、生成 artifact、评估诊断、分数，全部挂在每个节点上，且以"可回放"为设计目标从第一天就记录下来。这要求 evaluator 便宜、确定、可缓存，要求工作区可保存可恢复（策略要能"从父节点的 saved workspace 继续"），要求日志基建不是事后补的观测、而是系统的承重结构。**没有这份历史，dreaming 无处可梦**——方法论可以照抄，抄完发现手上没有 worlds。
- **三个域各自的高质量 evaluator 与 benchmark 设定**：Lasso 的 17 个合成实例 + 6 个跨生物/非生物的 held-out 下游数据集 + 客观值正确性检查（不通过则搜索分直接为零）；KernelBench 的正确性检查 + 逆运行时；三个数学问题的形式化目标函数。评分函数只要有一点可被 hack，回放分与在线表现就会脱钩，整个闭环立刻失效。
- **手工设计的初始 exploration policy 与 Gemini CLI 执行栈**：第 1 轮必须有一个能跑出像样树的策略，否则池子里第一份记录就没有价值，后面全无从谈起。
- **支撑 5–10 轮递归、每轮 110–640 次 agent 调用的算力预算**，以及 `M` 版策略 × `t` 棵树 × beta 网格的回放开销。

**迁移到其他域的通用启示**（我的分析）：这套东西的可迁移内核是一句话——**凡是"一次昂贵执行的结果被完整记录下来"的地方，都可以把它从一次性消耗品改造成可反复查询的评估台，然后把优化目标从"解"上移到"分配搜索的策略"。** 适用的前提是三个：结果可复现或至少可冻结、搜索是树状的（每步有明确的单一父状态）、单次尝试的产出与访问顺序无关。线上 A/B、压测、灰度发布、agent 批量跑分、SRE 故障演练都在这个范围里。反过来，第三个前提最容易被违反——一旦执行体在决策时读了全局历史（本篇的在线 prompt 恰恰这么要求），换序回放就是反事实错误的（§7.6）。所以真正该先问的不是"我能不能回放"，而是"**我的执行体到底有多依赖当时的全局上下文**"。
