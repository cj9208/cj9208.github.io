# 用 AI 打败 AI：快手柯南稳定性 Agent 的困难↔方案咬合，与"方法即通用件、Context 才是壁垒"

> 源文：《60% 用户渗透率、50% 完整采纳率：快手稳定性 Agent 如何落地？》，InfoQ，2026-09-07。嘉宾王泽锋（快手大前端稳定性方向技术专家），AICon 全球人工智能开发与应用大会（上海站）2026 分享。原文：<https://mp.weixin.qq.com/s/lqmVEaL1DHxuz6IlYqsbVw>
> 这是一篇读后梳理，不是翻译。主线一句话：**harness 配方是通用件（确定性归代码 / 概率性归模型 / Skill 承载私域 / 接口适配 Agent），真正不可复制的是 Context。** 这篇的价值不在架构图，而在证据——一套已经熟悉的 harness 逻辑，在一个上下文极难的垂直域真能跑到规模化采纳。
> 标注约定：§3–§6 的数字、案例、Skill 名、架构均为**源文原样**；§2"客户端为什么这么难"整节是**我的分析/领域常识，非源文**，已就地标注，用来解释困难集从哪来，不要当源文事实引用。

## 一、一句话主线

方法论层面没有秘密：他们自己也没造框架，直接用 Claude Agent SDK；"确定性归代码、概率性归模型、单次 LLM 别硬上 Agent"基本是反过度工程化的常识。**配方是可复制的通用件。** 文章自己的落点也在这——配方不是壁垒，Context 才是。把"知道 harness 逻辑"和"做出 60% 渗透 / 50% 采纳"拉开距离的，是那几块又脏又重、别人复制不走的活：端侧基建、源码服务、2 万行 Skill、Bad Case 闭环。

## 二、域背景：客户端稳定性为什么是个特别难的域（我的分析，非源文）

要理解后面每个方案在解什么，先得理解客户端稳定性的困难集从哪来。这一节是我的领域分析，源文只给了其中几条数据（已标注）。

**后端 vs 客户端，难在不同维度：**

- 后端的稳定性难题是"分布式的复杂度"（一致性、高并发、网络分区），但**环境可控、可回滚、可复现、有全链路追踪**——跑在你自己的机房，同质环境，坏了 5 分钟回滚全员生效。
- 客户端的难题是"**环境不可控 + 发布不可逆 + 现场易失**"——跑在用户手里成千上万种设备上（源文：100+ OEM ROM、1000+ 机型），厂商各自魔改系统；发版要过应用商店审核、用户不一定升级，线上同时躺着几十个历史版本；进程崩的瞬间现场就没了，只剩残缺 tombstone。

**"前端只是展示、逻辑应该远程调用"是误解——本地化是被物理约束钉死的（我的分析）：**

- **延迟**：UI 要跑 60/120fps，一帧预算 16ms/8ms。滚动、动画、点击响应、视频解码若每步远程调用一个来回（几十到几百 ms），界面卡成幻灯片。
- **弱网**：用户在地铁/电梯/无网。功能若靠远程调用，断网=白屏。客户端的核心价值之一就是弱网/离线自持。
- **电量**：每发一次网络请求要把无线电从 idle 拉到 active，radio 有"尾巴能耗"（tail energy），发完还会高功耗挂几秒。频繁远程调用比本地算更耗电。
- **成本**：客户端薄、逻辑全在后端，意味着几亿用户每次滑动都打到机房，后端账单爆炸。客户端本质是把算力和存储外包到用户设备上。
- 公道话：客户端本来就是混合的——**数据（推荐流、评论、关注列表）确实远程拉**；但拿到数据后的**渲染、解码、交互、缓存**必须本地。稳定性问题（SIGSEGV、UAF、主线程卡死）全长在本地这半段的 native/内存/线程层，这半段"调用"不掉。

**强耦合不是水平问题，是运行模型（我的分析 + 源文 ProGuard 案例）：**

- iOS/Android 的运行模型是"**一个 App = 一个沙盒进程**"。第三方 SDK（广告/推送/支付/APM）以库的形式编译链接进同一个二进制，不是独立服务。
- 真正的坑不是"塞进来"，而是**平台没有强制的进程隔离和资源配额**（不像后端有容器）。一个 SDK 崩了/漏内存/抢主线程，整个 App 陪着背。
- 源文案例：AI 生成的 ProGuard 配置带 `-dontoptimize` 写进 `consumerProguardFiles`，随 AAR 传到主工程与 R8 合并，关闭主工程全局优化 → DEX 膨胀 → APK +6MB。一个 SDK 的配置能拖垮主工程，正因为它们本就在同一构建产物里、配置会自动合并。
- 全局优化是**耦合放大器**（不是源头）：为启动速度/包体积/帧率/内存做的 R8 全局优化、共享内存池、主线程调度、跨模块复用，天生"牵一发动全身"，常被无意触发。

**两个数量级放大器（源文数据）：**

- **状态空间爆炸**：机型 × 系统 × 网络 × 内存 × SDK 组合 × 用户行为是天文数字。源文原话："没有任何测试矩阵能够在线下覆盖所有组合"，稳定性本质是"不完备性证明"问题。
- **高频变更**：强运营 App 一天 A/B + 灰度 + 运营变更 >1 万次。

**这一节的结论**（它决定了后面所有方案的形状）：客户端稳定性的难点不在"逻辑更复杂"，而在"**抓不到现场、改不动线上、复现不了**"。所以柯南 AI 的壁垒最终压在端侧基建和 Core Dump 上——它要解决的本质困难，就是在一个抓不到、复现不了、改不动的环境里，尽可能把崩溃现场的信息捞回来喂给 Agent。后端不需要这套重投入，因为后端的现场本来就抓得到、链路本来就追得回。

> 延伸（我的分析，非源文）：国产 App 耗电/后台常驻跟"代码塞一起"没有因果关系，是另一层面的事——① 推送基础设施缺失（国内没有统一 FCM，早年只能自己起常驻服务长连服务器）；② 保活军备竞赛/互相唤醒的囚徒困境；③ 部分主动作恶。属于"进程生命周期 + 推送机制 + 厂商博弈"，与"模块本地化"是两回事。记在这里只是防止把两个层面并成一个因果。

## 三、问题：AI Coding 之后，稳定性成了"最后一公里"

上游 Cursor / Claude Code / Codex 把研发吞吐拉起来了，但**告警、根因定位、止损、修复、经验沉淀**这条下游链路没同步提速。速率长期不对等，线上 Case 的数量、严重程度、处置时延都会劣化。

更棘手的是 AI 自身会制造新稳定性问题：**缺乏全局上下文的 AI 会沿"最小阻力路径"消除表面现象**（局部最优陷阱）——现象消失 ≠ 问题解决（ProGuard 6MB 案例见 §2）。前置约束（SDD、Coding Harness、Review）能拦一部分，但消灭不了全部。

结论（源文）：**线上稳定性处置，是完整落地 AI Native 的最后一公里。** 出发点——聚焦稳定性领域，"用 AI 打败 AI"。

## 四、困难 ↔ 方案 咬合（核心，按五层）

整套架构本质是"每个难点逼出一个对应件"。五层：应用层 → Agent 编排层 → Agent Harness 层 → 数据服务层 → 端侧基建层，纵向贯穿可观测与反馈迭代。

### 编排层：解决"任务性质不一样，不能一刀切"

| 困难 | 方案 | 为什么这么解 |
|---|---|---|
| 报警 SOP 严肃复杂，Agent Loop 会漏步/调错工具，报警场景不能接受 | **代码复刻 Workflow**，只在子环节引模型 | 确定性流程交给代码，模型不参与编排 |
| 简单任务硬上 Agent 是负优化：每多一轮 Loop 就多一次 LLM 请求 + Tool Call 失败 + 决策跑偏 | **单次 LLM 请求**（代码聚合数据→一次塞进 Prompt→结构化模板输出） | "快速分析"端到端稳定 <1 分钟 |
| 根因分析跨 5–10 个数据源、多次 Tool Call、无固定线性流程 | **Agent**（长链推理 + 按需加载 Skill） | 只有非线性、需动态扩展上下文时才值得付 Agent 的代价 |

原则：**确定性的归代码，概率性的归模型，能一次 LLM 解决就别上 Agent**。三种形态按任务难度分，不是叠 buff。

### Agent Harness 层：解决"私域知识缺失 + Agent 会跑偏/失控"

选型路径：AutoGen → 基于 OpenAI Agent SDK 的自研 Workflow → **最终敲定 Claude Agent SDK**。理由：工程红利（继承生产打磨过的上下文管理/工具使用）、随 Claude 迭代同步、对 Claude 适配深（国内开源模型走兼容协议）。

| 困难 | 方案 | 为什么这么解 |
|---|---|---|
| 通用 SDK 的 System Prompt 一堆稳定性无关噪声；工具太多易失控 | **精简 System Prompt + 注入硬规则**（区分推测/确定、标置信度、禁止跨类型无关联想）；**关工具 + Permission 沙箱锁 CWD** | 越界绝对路径直接拒，失控也控住影响半径 |
| 内部 SDK 从不在训练语料里（如崩溃兜底 SDK **Ekko** 的 Hook 栈帧其实是噪声，Agent 会顺着 Hook 追歪） | **Skill 里写明语义 + 排除规则** | 模型没见过的东西只能主动注入 |
| 字段语义已漂移，Agent 会自信地用旧规则出错（如 **FD OOM** 标签在新版 Android 已失效） | **Skill 里写成"禁止行为"** | 偿还历史技术债，防高置信度幻觉 |
| 跨端、跨异常类型上下文互相干扰 | **Skill 按异常退出类型切边界**（Android Java Crash / iOS Crash / Android Native Crash 各自独立） | 宁可重复建设，也不让上下文串味 |
| 2 万行知识塞不进上下文；专家不懂 Runtime 没法维护 | **Skill = Markdown + 渐进式披露 + 独立 Git 仓库** | 按需加载；专家只管写文档，能独立发布/灰度/回滚 |

Skill 规模（源文）：客户端已建 **30+ Skill，正文 + Reference 近 2 万行**。内容两类：**私域知识注入**（Ekko/FD OOM 那种）+ **根因分析 SOP（决策树）**：

- 鸿蒙 AppFreeze：先取卡死前多次采样堆栈比对 → 判断主线程是真阻塞还是繁忙到没及时处理窗口消息 → 若确认阻塞且在等锁，查全线程堆栈找持锁者。（参考华为系统 DFX 团队开源版）
- Native/C++ Crash **信号路由**：SIGABRT 优先看 Abort Message（典型是 Android Java Pending Exception 导致 Abort），SIGSEGV 才进反汇编 + 寄存器分析。这类核心决策逻辑既提效果又省耗时和 Token，但偏公域，随模型升级未来未必还要靠 Skill 注入。

### 数据服务层：解决"上下文取不到、取太慢、接口不 Agent 友好"

| 困难 | 方案 | 为什么这么解 |
|---|---|---|
| 崩溃堆栈跨 5–10 仓库，包名 ≠ 仓库名，光看堆栈判断不出该拉哪个仓库/分支/commit | **源码服务预聚合 + 预索引** | 提前解决"仓库找不到" |
| 主仓 git clone 几十秒到分钟级，每次重拉时延不可接受 | **同上，检索接近本地 grep 速度** | 把拉取成本一次性摊平 |
| 给 Agent 什么接口？定一堆 API Spec 太笨重 | **把面向人的 GUI 接口重包成 Bash 接口**（`git grep` / `git blame`） | 模型语料里全是 bash，天然熟，省掉 API 定义 |
| Bash 灵活但危险 | **源码只读挂载 + 完整命令日志 + 执行超时** | 自由探索但不许越界 |

演进方向（源文）：① grep → **LSP / Code Graph 语义检索**（NPE 要跨函数跨文件追生命周期、跨语言桥接，grep 不是最优）；② 单体 → **分布式**（源码服务日均数万次调用，已触单体扩展性瓶颈）。

### 端侧基建层：解决"高价值现场过去 ROI 太低没人消费"

| 困难 | 方案 | 为什么这么解 |
|---|---|---|
| Core Dump 对疑难问题（如 ART 虚拟机 JIT 机器码踩内存，PC 落在 JIT Code Cache，Tombstone 只 dump PC 附近数百字节不够）可能是唯一解，但几百 MB 二进制、结构复杂，只有少数资深专家能用 LLDB/GDB 挖几小时到几天，ROI 低所以过去没大规模建 | **AI 改变 ROI 公式**：Agent 自动反汇编关键内存段 + 关联源码/寄存器/日志 | 消费能力从"少数专家掌握"→"研发借 Agent 都能用"，端侧基建从"为人优化"转成"**为 Agent 优化**" |

本质（源文）：**Agent 无法凭空创造信息，上下文决定效果上限。** 端侧基建像冰山在水面下的地基，决定 Agent 能看到什么现场、能分析到什么深度。

### 反馈层：解决"AI 不知道自己不知道，人也不知道哪些没告诉 AI"

| 困难 | 方案 | 为什么这么解 |
|---|---|---|
| 幻觉根源是"不知道自己不知道"；同时人也未必意识到哪些暗知识还没喂进去 | **Bad Case 驱动闭环**：Case 管理（标注平台 + 统一采纳率标准 + 用户回访 + 专家二次确认，经典 Case 进评测集、缺陷转优化项）+ Case 总结（固定例会 Review、拉齐标准、共识优先级） | 用真实失败反推缺哪块 context，持续补 |
| 成本/性能/健康度看不清 | **三层观测**：链路层（还原一次调用的思考/工具/轨迹）+ 指标层（耗时/Token/成功率）+ 运营层（业务大屏） | 从单次调用到整体运营都能观测 |

### 还没解掉、正在探索的瓶颈（源文自认）

这两条说明**排障 ≠ 修复**，也标出方案边界：

- **思考深度不足**：遇到 NPE 只说"这里为空"，不沿数据流追是什么路径导致对象为空；信息缺失就幻觉。→ 短期靠 Skill/System Prompt 强约束 + **问题分级路由**（难问题给强模型），长期靠**树形搜索**（围绕多个根因假设并行收证据，代价是 Token）。
- **修复明显落后于排障**：Agent 缺历史修复经验，业务暗知识（能不能改、怎么改合规）只在人脑里，既不在堆栈也不在文档。→ 探索 **Memory 体系**，前提是人先把业务知识持续显性化——"没被表达的知识就无法成为上下文"。

## 五、标杆案例：鸿蒙 C++ Crash 纯系统堆栈，约 10 分钟定位（源文）

把推理链路走一遍，正好体现"困难↔方案"如何在一个真实 Case 里咬合：

- **现象**：SIGSEGV + 崩溃地址很大 + 每个栈帧都来自系统 so → 典型踩内存、纯系统堆栈。过去只能平台型稳定性团队介入。
- **流程**：报警发生 → IM 机器人串联处置流程 → 柯南 AI 约 10 分钟定位 → 团队据分析结果讨论、**关掉一个开关完成止损**。
- **推理阶段**（每步对应一个已注入的能力）：
  1. Skill 信号路由：SIGSEGV → 进内存分析流程；
  2. 寄存器分析 → 判定大概率 Use-After-Free；
  3. 分析业务日志共性 → 收敛到某内部基础组件，发现关键动作与线程销毁有关；
  4. **得益于注入的私域知识，正确排除了日志噪声**，没被无关信息带偏；
  5. 按日志线索定位源码 → 寄存器 + 日志 + 源码三方证据组合成自洽证据链 → 高置信度结论。
- **底层根因**：系统库 libuv 中某个 Async Handle 发生 Use-After-Free。**触发链路**：某内部基础组件加载资源文件失败后执行了一次销毁动作，最终引发崩溃——这个信息把问题收敛到内部特定业务，并在其中找到止损开关。
- 另一例：WWDC 后 iOS 27 推送，小规模堆栈报警，快速分析发现 100% 集中在 iOS 27，很快收敛到某内部工具的新系统兼容性问题。

## 六、效果（源文数字）

- 内部大前端研发**用户渗透率 ≈ 60%**；根因分析结果**完整采纳率稳定在 ≈ 50%**。
- 快速分析场景端到端**稳定 <1 分钟**；标杆鸿蒙 C++ Crash **约 10 分钟**定位。
- 角色变化：稳定性专家从"**前线救火员**"→"**消防系统设计师**"——不再亲自排每个问题，而是沉淀 Skill、共建 Context、驱动 AI 上一线。

## 七、收束：方法是通用件，Context 才是壁垒

源文沉淀的五点认识：

1. 确定性的归代码，概率性的归模型——组合 Workflow / 单次 LLM / Agent，避免过度 AI 化。
2. Agent Harness 选型要轻量化、领域化——基于成熟 SDK，用 Skill 承载专家经验，不重造通用底座。
3. 数据服务关键是提供 Agent 友好的接口——Bash 是有效形态，但必须配权限与安全边界。
4. 上下文决定 Agent 的效果上限——端侧基建决定能看到什么、能分析多深。
5. 反馈迭代决定长期表现——Bad Case 闭环必须常态运行。

**我的判断（可迁移 vs 不可迁移）：**

- **可复制的通用件**：五层架构、"确定性归代码/概率性归模型"、Skill 承载私域知识、Bash 接口、Permission 沙箱、三层观测——这些是任何做过 Agent 编排的人都能照搬的方法论，没有秘密。
- **不可复制的壁垒**：三端 Core Dump 采集+消费基建、预聚合的源码服务、30+ Skill / 2 万行私域知识、以及"专家持续把暗知识显性化"的组织习惯 + Bad Case 闭环。源文原话："Context 才是真正的壁垒，也是享受模型升级红利的前提。"
- 所以这篇真正值得盯的，不是那张架构图，而是那道**磨人的坎**：持续把私域知识搬进 Agent 能消费的地方。方法论早就熟了，难的是把 context 工程日复一日做下去——这也是"知道 harness 逻辑"和"跑到 60% 渗透"之间的全部距离。
- 迁移到其他垂直域（不限稳定性）的通用启示：**先分清哪些是确定性流程（交给代码/Workflow）、哪些真需要长链推理（才上 Agent）；再把领域专家的隐性判断显性化成按需加载的知识；最后用真实失败案例驱动闭环。** 模型会持续变强，红利只留给那些已经把 context 底座打好的人。
