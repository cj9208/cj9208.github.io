## 三、P0：会造成静默失效或冲突

**P0-1 Claude Code 的接入路径未定。** 它只读 `.claude/skills`，而 OpenCode 项目级同时扫 `.opencode/skills`、`.claude/skills`、`.agents/skills` 且要求跨根名字唯一。因此**不能**简单建一个 `.claude/skills` 联接——那会让 OpenCode 看到两份同名技能。三条待选：确认 OpenCode 的重名行为到底是报错还是按优先级择一（读源码或实测）；改用 per-skill 联接并验证 OpenCode 去重；或接受"用 Claude Code 时它只看得见 `.claude` 里显式挑出的子集"。**当前状态：已给 AGENTS.md 下了"禁止手工创建 `.claude/skills`"的硬约束，脚本的 check 也会把它报成 DUPLICATE ROOT。**

**P0-2 联接的实际可用性——已验证通过（2026-10-26）。** 验证方法没有靠推断：在 `.agents/skills/junction-probe/` 放了一个一次性探针技能，下一轮对话的可用技能清单里出现了它，即证明 harness 能透过目录联接读到正本；验证后探针目录已删除，正本回到 19 份。**顺带得到一个比预期更好的结论：Qoder 是每轮重新扫描的，新增技能不需要重启会话就生效。** 这同时意味着原先担心的"`.qoder/skills` 换成联接后要重开会话"这个风险不存在，`--mode copy` 兜底路径目前没有任何已知的需要启用它的场景。

**P0-3 一条已知的删除风险。** `.qoder/skills` 是重解析点，在 Git Bash/MSYS 里 `rm -rf .qoder/skills` 可能穿越联接删掉正本。已在 AGENTS.md 与脚本 docstring 里写明必须用 `unbind`；但这是"文档约束"而非"机制约束"。真要机制化，得在脚本里加一层防误删（例如 bind 后给 `.agents/skills` 设只读属性）——**本轮故意没做，属于欠账**。

## 四、P1：触发与产物形状（有一手实验依据）

**P1-1 描述里不该有流程摘要。** 证据：superpowers 的 writing-skills 记录过实测——描述写了 "code review between tasks"，流程图规定两次 review，实际只跑了一次；修法是**把流程从描述里删掉**，机制是"描述一旦概括流程，agent 照摘要走、不读正文"（渐进披露陷阱）。命中对象：`digest-article`（描述含"先抓正文→失败降级 browser-use→对话给摘要→确认后落盘"的完整链路 + 一句元规则"全程严格区分源文事实与我的分析"，后者属于正文）、`review-blog-content`（497 字符里塞了类型分类逻辑）、`search-blog-articles`、`sync-zhihu-migration-status`。目标形状：`<做什么>. 触发：<用户会说的动词/短语>. 不用于：<最易误选的相邻场景> → <相邻 skill 名>.`

**P1-2 11/19 个技能没有任何"何时不用"。** 列表：`stress-test-reasoning`、`add-hugo-front-matter`、`search-blog-articles`、`restore-missing-links`、`capstone-*`（build-expertise / fieldwork / coaching-core / compare-opportunities / generate-article 对应项）、`sync-zhihu-migration-status`、`pipeline-blog-init`。依据：Claude Code 与 Codex 的官方写法要求都把"何时不使用"列为描述必备成分；SkillsBench 归纳的三种伤害里，第二种就是"技能覆盖掉模型本来更强的策略"，给出的对策原话是"include applicability boundaries, not just preferred procedures"。你那 6 个 `capstone-*` 相互之间边界只写在各自描述开头一句话（"Use when…"），近似反例缺位——这是同族技能最容易互相误选的形状。

**P1-3 判断型技能用了禁令而不是正面配方。** 计数最高的三个：`digest-article` 19、`add-hugo-front-matter` 12、`review-blog-content` 12。依据是 superpowers 的对照实验结论：**"产物形状错"这一类失败，禁令那一组实测反而产出更多不想要的内容**，正确写法是正面配方——"产物是什么、由哪几部分、按什么顺序"。这条对你特别对症，因为你偏好的表达方式本身就是禁令式（"不要评分表""不要元叙事""不要散"）。修法是把每条禁令翻译成一个形状描述，而不是删掉。

**P1-4 编排技能可能重述了被编排者的纪律。** `pipeline-blog-init`（88 行、1 个 H2、0 反触发）依次调 3 个技能。依据 mattpocock 的分线规则：user-invoked 只负责编排，model-invoked 才持有纪律，**编排技能不得调用另一个编排技能**，也不得复述被调用技能的内部步骤（复述=同一规则出现两份，从此开始漂移）。待核对：它是否把 `add-hugo-front-matter` / `rename-blog-filenames` / `sync-subfolder-links` 的步骤抄了一遍。

## 五、P2：结构与体量（依据较弱，但便宜）

**P2-1 7/19 个正文零个二级标题。** `stress-test-reasoning`（96 行 / 9389 字符的纯段落流）、`capstone-coaching-core`、`capstone-build-expertise`、`capstone-project-framing`、`capstone-deepen-opportunity`、`capstone-compare-opportunities`、`generate-article`。规范给的形态是"过程用祈使句 + 可勾选清单 + 检查点"。`stress-test-reasoning` 优先级最高：它是你最常在对话里手动调用的那个。

**P2-2 验证步骤需要设上限并标"可选/快路径"。** `sync-subfolder-links` 验证类词 12 次、`review-blog-content` 11 次、`add-ez-encoder-presentation` 10 次。依据是三篇论文的收敛点：307 例技能致因失败里**最大单一原因是"过度验证"（67 例）**，第二是重型实现流水线（30 例）；SkillsBench 给的对策原话是"mark optional steps and supply a fast path"。注意：这条不是说你的验证习惯错，而是说**写进技能之后它会变成强制工作**，两者的代价不一样。

**P2-3 `add-hugo-front-matter` 是唯一接近体量线的（259 行）。** 规范的拆分触发条件是"When SKILL.md becomes unwieldy, split into separate files"，并把参考内容按变体切（`references/aws.md`、`gcp.md` 那种），使 agent 只读到需要的一份。它里面那 12 条禁令（P1-3）和命名规范细则，多数属于"被选中后才需要"的参考资料。

**P2-4 文件位置问题（两处）。** `add-hugo-front-matter/tags-registry.md` 放在技能根目录，不在 `references/` 下；`search-blog-articles/index.json` 是 299KB 的生成物，也在技能根目录。规范把参考文档归 `references/`、把模板与资源归 `assets/`，且引用要保持一层、写成**条件式**（"若 X 则读 references/Y"）而不是笼统的 "see references/"。生成物放在根目录还有一个额外代价：它会随 skill 目录被复制、打包和 diff。

## 六、真正的缺口：没有判据回路

以上都是"我认为"，唯一能把它们变成"测出来"的做法是官方那套：带技能/不带技能成对跑（`evals/evals.json`，先 2–3 个用例，断言在第一轮跑完之后再补），触发用约 20 条查询、8 正 8 近似反例、每条 3 次、阈值 0.5、60/40 训练/验证切分。评估看**通过率与 token/时间的双 delta**——"高 2 个点但 token 翻倍"未必值得。还有一条反直觉判据：**加规则后通过率持平，说明技能过约束，该删而不是该补。**

这条排在所有条目之后做才对：先有装订层稳定，再谈测量；但它是让 P1/P2 不再靠手感的前提。基准数也支持"别指望一键变好"：SWE-Skills-Bench 里 49 个公开技能 **39 个通过率零改善**、均值 +1.2%；SkillsBench 里 curated 技能从 33.9% 提到 50.5%，但 87 个任务中仍有 13 个是负 delta。

另有一条要长期警惕的机制：SkillsBench 中用 skill-creator 批量自造的技能落在**无技能基线以下**（−8.1 到 −11.5pp），三个成因之一是"自信但错误的 gotcha 会变成承重结构"。你技能里那些"我在实践中踩过的坑"式断言，正是技能唯一该提供的东西（模型自己推不出的项目特有知识），但一旦某条过期或当初就记错，模型会照着它坚决地做错且难以察觉。SWE-Skills-Bench 里 3 个技能退化最高 −10%，原因写的是"版本不匹配的指引与项目上下文冲突"。**建议：每半年把 19 个技能里的"事实断言"逐条对源码/官方文档过一遍，而不是只改文案。**

## 七、优化时的顺序建议

P0-2 已于 2026-10-26 用探针验证通过（见该条），不再是待办。剩下的顺序：**P0-1**（Claude Code 要不要接、怎么接）→ **P1-1 与 P1-2**（这两条直接改变触发准确率，且改动只在 `description` 字段，风险最低）→ **P2-1**（结构）→ **P1-3、P1-4** → **P2-2/3/4** → 最后建第六节那套判据回路，用它验收前面所有改动。

不合并、不删除任何技能之前，先跑判据——`capstone-*` 六个和 `sync-*` 三个看起来像可以合并，但没有测过的合并等于把有效部分一起扔掉。
